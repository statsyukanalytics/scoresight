# Scoreboard OCR and NHL timing

The pipeline reads the broadcast clock and period with the existing ScoreSight PP-OCR recognizer, keeps decoded frame timestamps, and joins them to CapAngry's `expanded_play_by_play` and `player_shifts` tables. It keeps every fetched record, including events that do not appear in the uploaded clip.

## Local run

Install `requirements-scoreboard.txt` and put FFmpeg and FFprobe on PATH. Download the pinned models with `python -m studio.scoreboard.fetch_models`. Set `NHL_DATABASE_URL` to the NHL database connection string through your environment. Queries run in a read-only transaction.

```powershell
python -m studio.scoreboard --video game.mp4 --config studio/scoreboard/profiles/tsn-2026-720p.json --game 2026020292 --output clips/game/scoreboard
```

Use a new output directory for each run. The profile must match both the broadcast layout and video resolution. Existing profiles are copied from `nhl-tracking-data/configs/scoreboards`. Different layouts need measured clock and period rectangles. No automatic broadcast-layout detector is claimed.

Outputs include raw OCR, `observations.csv`, a runtime summary, and `nhl-timeline.json`. Each event and shift retains its original database record and gains candidate video intervals. Missing or low-confidence clocks break continuity. No interpolation crosses an unreadable sample or a large clock jump. Stopped clocks and repeated footage can match multiple intervals. These are clock candidates requiring review, not verified live-play timestamps or frame-exact event locations. Shootouts are left unmatched.

## Clip uploads

The companion app changes are in `statsyukanalytics/statsyukreactv2` (PR #225): `NhlClipForm.tsx`, the clips API route, and `packages/domain/src/clips/nhl-clip.ts`. The form asks for a scoreboard layout and includes `scoreboardprofile` in the uploaded object's metadata, alongside the existing NHL game ID.

`studio.scoreboard.service` receives a Google Cloud Storage finalized event. It processes only objects in `videos/` with the NHL clip marker and a supported scoreboard profile. It reads the exact object generation, runs OCR and alignment, and saves results under `scoreboard/<nhl-game>/<generation>/<source-name>/`. It sets `nhltimeline` on the source object's metadata to the result's GCS URI. A completed result makes delivery retries skip processing. It does not start another tracking run or change NHL database records.

The worker image is defined in `scoreboard.Dockerfile`. Deploy it to `grounded-jetty-485516-r2` as an authenticated Cloud Run service, with concurrency 1, maximum instances 1, a 3600-second request timeout, and adequate memory for the source video (temporary storage uses instance memory). Use an Eventarc `google.cloud.storage.object.v1.finalized` trigger for `statsyuk-game-videos`. Grant its trigger identity Cloud Run invoker; the worker identity needs source-object read/update, result-object create/read, and access to the secret containing `NHL_DATABASE_URL`. Do not enable unauthenticated invocation. Deploy the companion app changes as well.

The worker is deployed as `scoreboard-ocr` in `grounded-jetty-485516-r2/us-central1`; Eventarc trigger `scoreboard-ocr-upload` receives finalized uploads from the video bucket. The service is private, uses the dedicated `scoreboard-ocr` service account, and reads secret version `nhl-scoreboard-database-url:1`. Its bucket role allows object get/create/update only under `videos/` and `scoreboard/`. The trigger subscription has a 600-second acknowledgement deadline. The companion app integration is [PR #225](https://github.com/statsyukanalytics/statsyukreactv2/pull/225), on the isolated `codex/scoreboard-ocr` branch. The upload selector integration was merged in PR #225. The new film review interface is pending review in PR #227. ## Provenance and checks

The recognizer and model-fetch script come from ScoreSight commit `90b9d92be9afd45eeee916219973dab621d4f5ab`; its license is preserved in `SCORESIGHT-LICENSE`, and model license/notice are under `ocr_models/ppocr/`. The recognizer uses standard logging and configurable resource paths instead of desktop-app logging. The extraction script is ported from `nhl-tracking-data/scripts/ocr/extract_clock.py` and uses ScoreSight's CPU runtime rather than requiring CUDA.

`python -m unittest discover -s tests -p test_scoreboard.py -v` checks missing readings, clock stoppages, repeated footage, regular/playoff overtime, shift boundaries, and low-confidence parsing. A three-second video fixture produced six valid OCR observations with frame timestamps. A read-only database smoke check loaded 318 events and 740 shifts for game 2026020292. Cloud verification on 2026-11-11 also passed: a synthetic 720p upload automatically produced six valid observations, five clock intervals, 318 events and 740 shifts. The fixture matched two start-of-game events and twelve shifts; these verify the join mechanism, not real broadcast accuracy. The generated fixture and result objects were removed after verification. Domain and web TypeScript checks passed.

## Full-game timeline v2

Schema version 2 retains every event and shift with candidate, ambiguous (separated video occurrences), or unmatched status. Each clock interval carries event and shift indexes for reverse lookup while scrubbing. Held clocks are not proof of a stoppage: integer clock quantization also repeats readings. Same-clock boundary groups retain NHL sort order and distinguish stop/restart roles without inventing exact video frames. Gaps cover unobserved video, clock reversals (possible replay), period transitions (possible intermission), and the unsampled tail. Shootout clocks remain unsupported; multiple playoff overtimes are parsed. A single occurrence is still only a candidate, never verified live footage.

Game-scoped enrichment includes raw event payloads, shot context, goal visualizer rows when present, player identities, teams, season rosters, skater/goalie game logs, player game xG, season statistics, draft picks, and contracts. Enrichment failures are reported by source and SQLSTATE; empty sources stay empty. Season/player context is not itself timestamped. The GAR join view is deliberately not used because it restricts season, game type, shots, and goalies.

The companion app adds /internal/clips/[gameId]/film, reusing GameReportShell and VideoSlot. Staff can filter events/shifts, choose among separated candidates, inspect unmatched records and database context, and see candidate on-ice players at the playhead. Source URI, object generation, and NHL game identity must match before a result is displayed. Existing tracking film routes remain available. Results v2 use scoreboard/v2/<game>/<generation>/<filename>/ to avoid reusing old v1 outputs. Old uploads need a new worker invocation or reupload; a source relocation alone does not rerun them.

Validation: ten alignment unit tests; read-only enrichment for game 2026020292 (318 events, 740 shifts, 95 shot-context records, 38 players; no failed enrichment queries); a three-second synthetic video through the full OCR/database CLI (six valid observations, five intervals, explicit 0.5-second unsampled tail). Real full-broadcast accuracy and long-video resource usage still require validation. The Cloud Run worker retains its existing execution/time/memory limits.

The shift table also contains type-505 zero-duration goal markers. These are aligned as point records and indexed separately from on-ice shifts. A full three-period simulated clock matched all 318 events, 738 actual shifts, and two goal markers for the test game; eleven unit tests pass. This is a database/clock coverage check, not broadcast accuracy evidence.

## Automatic scoreboard discovery

The CLI defaults to automatic discovery when --config is omitted. NHL uploads default to scoreboardprofile=auto; the upload form no longer asks for a layout. Existing explicit profiles remain available for manual CLI/API overrides. The worker packages ScoreSight's hash-pinned D-FINE-S layout model. It searches the full picture and quadrants to resolve small broadcast overlays, reads candidate fields with PP-OCR, and identifies clock/period by valid text instead of trusting detector role labels. Competing clock candidates or missing fields remain unreadable. Detected boxes are re-read every sample, rediscovered every ten seconds, and invalidated immediately when OCR becomes invalid; failed searches retry after two seconds at 2 Hz. Full-video detection is not a guarantee of broadcast coverage or live/replay classification.

Per-sample detected boxes are stored in layout-observations.json. The artifact prefix is scoreboard/v2-auto/<game>/<generation>/<filename> so older results are not silently reused. Model provenance and license are included beside the worker.

Validation: four automatic-field tests cover missing/low-confidence periods, competing clocks, semantic field assignment, and disappearing scoreboards. A local 46.21-second 1920x1080 TSN WSH/OTT broadcast clip produced 49 accepted readings from 93 samples without a layout. A frame at five seconds visibly showed 7:34 / 3RD and OCR agreed; a frame at twelve seconds had no scoreboard and was left unreadable. Local execution took about 13 seconds. This is one broadcast example, not a broad accuracy evaluation.

## OCR-only game library

New uploads use `scoreboard/sources/<team>/<game>/<video>-<filename>`. The deployed tracking validator returns before doing any work for paths outside `videos/`; OCR sources therefore cannot dispatch tracking. The OCR receiver accepts this new prefix and legacy `videos/` sources, but ignores its result prefix. Existing full-game source generations remain unchanged. The companion app moves upload and Gemini tools to `/internal/clips/dashboard` and makes `/internal/clips` the game picker, initially including only the Minnesota–Montreal test game. New OCR uploads join that library. Upload completion verifies the finalized source before marking it uploaded; tracking is never invoked.
